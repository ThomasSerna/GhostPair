# Future Heroku migration

This is a preparation and activation runbook, not a deployment record. Production remains **https://ghostpair.onrender.com** with Render Auto-Deploy **After CI Checks Pass** on `main`. No Heroku app, database, credit allocation, backup schedule or store submission is created by the repository changes. The landing stays on GitHub Pages.

## Target and account prerequisites

Use a Cedar Common Runtime app in the US region, stack `heroku-24`, the official `heroku/nodejs` buildpack, **one Basic web dyno ($7/month)** and **Heroku Postgres Essential-0 ($5/month)**. The current total is $12/month before other resources or charges. Essential-0 has 1 GB storage and 20 connections; GhostPair's pool uses four. Rooms remain in memory, so do not scale web beyond one, enable autoscaling or Preboot. Basic avoids Eco's idle sleep. See [pricing](https://www.heroku.com/pricing/) and [Postgres plans](https://devcenter.heroku.com/articles/heroku-postgres-plans).

Before creating billable resources:

1. Complete Heroku account verification, enable account MFA and connect the approved GitHub Student Developer Pack account to the [Heroku student offer](https://www.heroku.com/github-students/).
2. Add a valid debit/credit card and wait until Billing confirms the student allocation. The offer is $13/month for 24 months; unused monthly credit expires and resources exceeding the credit, or retained after the program, are billed to the card. GitHub student approval alone does not activate Heroku credits.
3. Confirm that the available credit covers this app and any other account resources. Recheck current pricing before activation; do not add paid logging, staging, Redis or review apps for this migration.
4. Finish the [publication requirements](publishing.md), including the Google publisher account, support address and manual browser checks. Heroku verification and Chrome Web Store registration are separate.

The intended URL is the real Heroku-assigned HTTPS address. Cedar uses `APPNAME-IDENTIFIER.herokuapp.com`, where the identifier is generated by Heroku; do not guess `ghostpair.herokuapp.com`. Record the actual Web URL from `heroku apps:info` after creating the app. Avoid renaming or recreating the production app because that changes its address. See [app URLs](https://devcenter.heroku.com/articles/app-names-and-subdomains).

## Runtime and build

The root package constrains Node to `>=24.13.0 <25`. `heroku-postbuild` compiles only `@ghostpair/signaling`; the root `Procfile` starts `node apps/signaling/dist/main.js`. Heroku installs build dependencies and prunes them afterward. This hook is not an npm install lifecycle script and does not change the existing Docker/CI build. Do not set `NPM_CONFIG_PRODUCTION=true` before compilation. No release-phase identity import is needed: startup creates `devices` only if absent. See [Node support](https://devcenter.heroku.com/articles/nodejs-support) and [build behavior](https://devcenter.heroku.com/articles/nodejs-classic-buildpack-builds).

Configure the runtime values from [`deploy/heroku.env.example`](../deploy/heroku.env.example) as Heroku config vars:

- `HOST=0.0.0.0`, `NODE_ENV=production`, `TRUST_PROXY=true`.
- Use the add-on's managed `DATABASE_URL`; never commit it, print it, put it in `VITE_*`, or replace it with the example's empty value. Heroku supplies `PORT` and `DYNO`; leave them unset in your own configuration. Startup rejects a Heroku environment without PostgreSQL instead of using ephemeral SQLite.
- Set `DATABASE_SSL_MODE=verify-full` and `DATABASE_SSL_CA_FILE=/usr/lib/ssl/certs/ca-certificates.crt`. The Heroku stack includes the AWS RDS certificate authorities used by Essential Postgres. Keep certificate and hostname verification enabled. Do not disable TLS or set `rejectUnauthorized: false`.
- Keep TLS and bounded timeouts in the explicit application configuration; do not add `ssl*`, `uselibpqcompat`, query/statement/connection timeout overrides or `options` to the managed URL. If a provider URL contains unsupported options, resolve that before activation rather than weakening validation.

Heroku can rotate database credentials: use the managed URL, not a copied permanent connection string. The stack CA path applies inside Heroku; external PostgreSQL clients need their own trusted CA file. See [Postgres connections and certificates](https://devcenter.heroku.com/articles/connecting-heroku-postgres).

`TRUST_PROXY=true` is appropriate only behind the controlled Heroku router. GhostPair uses the rightmost forwarded address when it is a valid IP, matching the IP Heroku appends; do not change this to trust a caller-supplied first IP. The existing 30-second WebSocket heartbeat is below Heroku's 55-second idle limit. `SIGTERM` closes signaling and database connections; Heroku allows 30 seconds before forced shutdown. See [routing](https://devcenter.heroku.com/articles/http-routing) and [dyno shutdown](https://devcenter.heroku.com/articles/dyno-shutdown-behavior).

## Activation and data transfer — future operations

Perform these steps only after account/credit verification and an explicit request to activate the migration. Keep Heroku automatic deployment **Off** while configuring and testing. Preserve Render's **After CI Checks Pass** setting; preparation does not change Render or its PostgreSQL database.

1. Create the US Cedar app with `heroku-24`, select the official buildpack and provision `heroku-postgresql:essential-0`. Record the actual app name and Web URL. Configure runtime variables, keep maintenance mode enabled during the cutover and do not deploy the server yet: the destination must be empty for the restore.
2. Select a commit from `main` whose CI checks passed. Run `npm ci`, `npm run typecheck`, `npm test` and `npm run test:heroku` locally/CI. The last command compiles fresh sources using `heroku-postbuild` in a disposable directory, prunes development dependencies, and checks the runtime against isolated PostgreSQL through restart and shutdown. It uses Docker, or an existing PostgreSQL bin directory set in `GHOSTPAIR_TEST_POSTGRES_BIN`; Windows emits the signal through a test-only IPC bridge, while Linux sends real `SIGTERM`. The full existing production/store build must also pass. Keep database secrets out of these builds.
3. Arrange a short cutover window. Stop new pairing and stop the source signaling writer before taking the final backup; keep its database intact. Existing direct WebRTC sessions may outlive signaling, but new pairing is unavailable until the destination is ready. Do not run both services against the same live registrations during this transfer.
4. Use PostgreSQL's `pg_dump`/`pg_restore`, not `npm run migrate:identities` (which imports SQLite). GhostPair's persistent application data is the `public.devices` table; export that table without provider-owned schemas or extensions. Use a client compatible with the source server version and restore to an equal or newer supported PostgreSQL version. Store the backup in a private directory outside the repository, with restricted access and encrypted storage. Never pass passwords or complete credentialed URLs on command lines or in shell history.

Configure private `PGSERVICEFILE` and `PGPASSFILE` files outside the repository for service names `ghostpair_source` and `ghostpair_heroku`. Each service defines its host, database, user and verified TLS settings; the password file contains the corresponding password. On Windows use absolute paths and restrict their access to the operator. The local destination service needs the official AWS RDS CA bundle; the dyno's CA path is not a local Windows path. See [PostgreSQL service files](https://www.postgresql.org/docs/current/libpq-pgservice.html), [password files](https://www.postgresql.org/docs/current/libpq-pgpass.html) and [Heroku external access](https://devcenter.heroku.com/articles/connecting-to-heroku-postgres-databases-from-outside-of-heroku).

With those variables already configured privately, run from PowerShell:

```powershell
$backupPath = Read-Host 'Absolute path for the private cutover backup outside Git'
pg_dump --dbname=service=ghostpair_source --table=public.devices --format=custom --no-owner --no-acl --file=$backupPath
if ($LASTEXITCODE -ne 0) { throw 'Source backup failed; do not continue.' }
pg_restore --dbname=service=ghostpair_heroku --no-owner --no-acl --single-transaction --exit-on-error $backupPath
if ($LASTEXITCODE -ne 0) { throw 'Restore failed; keep the source intact.' }
```

The destination must be empty. Do not add `--clean`, drop the source table or reset extension storage to resolve a restore error. The transaction prevents a partial restore. Verify the `devices` row count and preservation of IDs, credential hashes and timestamps through private read-only checks; do not publish row contents or credentials. Test restoring this backup before relying on it for rollback.

5. Deploy the verified commit manually. Set the process formation to exactly **one Basic web dyno**, with no worker or extra process. The server must bind Heroku's assigned port and initialize the restored database. Disable maintenance mode for endpoint checks, keeping the new address unadvertised: Heroku returns 503 on public routes while maintenance mode is enabled. Confirm `GET /health`, `GET /ready` and `GET /privacy` return 200 from the actual HTTPS URL. A failing database/TLS configuration must prevent readiness; do not work around it with SQLite.
6. Use isolated test profiles to check registration, valid extension origins, rejected web origins, WebSocket pairing and a real session across two networks. Restart the Heroku app and confirm the same Heroku installation code still authenticates. Verify shutdown/restart behavior, host consent, control withdrawal and disconnect. There is still no TURN relay; some networks remain unsupported.
7. Update public production defaults to the verified Heroku URL: `.env.production`, the official server preset in `apps/extension/src/connection-presets.ts`, installation instructions, privacy/service details and any matching assertions. Build a new extension version with matching root/workspace/manifest versions and release notes, then run `npm run package:store`. Do not change defaults to a placeholder or an unverified endpoint. Existing manually saved settings require an explicit switch to the new official server; a rebuild alone does not replace them.
8. When acceptance checks pass, keep maintenance mode off, publish the verified extension update through the normal store review, and configure Heroku's GitHub integration on `main` with **Wait for CI to pass before deploy**. Verify the deployed commit. Keep Render stopped as the rollback target during the agreed transition; do not delete it or its database as part of preparation. See [GitHub deployment integration](https://devcenter.heroku.com/articles/github-integration).

### Installation identity and rollback

The extension stores credentials per signaling URL. Moving from Render to the Heroku URL creates a **new connection code**, even when the server database is copied. A Chrome Web Store installation also has a different extension origin/storage from an unpacked development installation, so users must not expect their unpacked code or settings to transfer. Do not promise automatic preservation across these boundaries or silently copy credentials. The server accepts any valid Chrome/Edge extension ID; a store ID does not require a server allowlist change.

Retain the previous production build, source database and private cutover backup until acceptance and rollback have been verified, then delete the manual backup as soon as it is unnecessary and no later than **30 days after its creation**. Record that deadline when exporting. Retain no extra snapshots indefinitely. If Heroku activation fails before new registrations, restore the previous build/endpoint and resume the intact source service. If new identities have been registered, preserve the current destination and reconcile those records before any database rollback; restoring an older snapshot loses later registrations. A store update containing a wrong endpoint requires another reviewed version, so test before submitting. A rollback of the web code does not roll back database data or already-installed extension defaults.

## Backups, logs and deletion after activation

Heroku PGBackups is included; no paid scheduler/add-on is required. After activation, capture and download a manual backup to verify recovery, and schedule a daily backup using the actual app name:

```powershell
$appName = Read-Host 'Existing Heroku app name'
heroku pg:backups:capture --app $appName
heroku pg:backups:info --app $appName
heroku pg:backups:schedule DATABASE_URL --at "02:00 America/Bogota" --app $appName
heroku pg:backups:schedules --app $appName
```

Check every exit status and the completed backup before proceeding. Essential keeps up to **five manual backups**, **seven daily backups and one weekly backup**, with no monthly retention. Manual backups do not expire merely because they are old: review their dates and delete each when no longer needed, within 30 days, using `heroku pg:backups:delete <backup-id> --app <actual-app-name>`; delete downloaded copies on the same schedule. Check scheduled backup success manually because failures do not send notifications. Recheck the schedule after changing database attachments or restoring into a replacement database. See [PGBackups](https://devcenter.heroku.com/articles/heroku-postgres-backups).

Cedar Logplex retains at most the latest **1,500 lines**, expiring after **one week**; high log volume can evict lines sooner. Application counters do not record payloads, passwords or connection URLs, but Heroku router logs can contain IP addresses and request metadata. Do not add log drains or retain downloaded logs beyond the published policy. The current Render provider's retention must be checked separately; these Heroku limits do not describe Render. See [Heroku logging](https://devcenter.heroku.com/articles/logging).

For a deletion request, identify both the service URL and the requested connection code. Possession of the public code alone is not proof. Ask the requester to host a fresh temporary session from that installation, with that code and a temporary password, and verify the hosted session through the ordinary extension flow. End the session, then delete only the verified `devices` row with a parameterized operation and confirm the affected row count. Never request owner credentials/tokens, session passwords, permanent passwords or a dump of extension storage by email. If control cannot be demonstrated, request another verifiable route before deleting somebody else's registration.

Removing the server row does not erase local settings, peer copies or old backups. Explain that re-registration creates a new code; do not remotely reset the user's extension. Remove copies under the operator's control, and let scheduled backups expire within their retention window. Keep the minimum necessary deletion reference privately until all relevant older backups are gone, reapply outstanding deletions before bringing any restored backup online, then remove that reference. Keep the published [privacy policy](privacy.html) consistent with the actual configuration; do not claim these future Heroku operations already run on Render.
